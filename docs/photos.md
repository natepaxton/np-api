# Photos

A `Photo` is an image stored in Cloudinary plus what we know about it: who took it, when, where,
and its tags. Source: `src/NpApi.Api/Features/Photos/`.

## Model

| Field | Type | Notes |
| --- | --- | --- |
| `Id` | `uuid` | GUID v7, generated by the API (see below) |
| `CloudinaryPublicId` | `varchar(255)`, unique | e.g. `np-api/photos/0199…`. One asset maps to one row. |
| `Url` | `varchar(1024)` | The `secure_url` Cloudinary returned for the original |
| `Filename` | `varchar(255)` | Original file name, informational only |
| `PlaceId` | `uuid?` → `places.id` | The named place it belongs to. See [places.md](places.md). |
| `CameraOwnerId` | `uuid?` → `people.id` | Whose camera took it (not necessarily who uploaded it). See [people.md](people.md). |
| `Latitude`, `Longitude` | `double?` | Both or neither, range-checked by the database |
| `LocationSource` | `Exif` / `Inferred` / `Manual`, nullable | Set exactly when coordinates are set |
| `DateTaken` | `timestamptz?` | A real instant, stored as UTC |
| `DateCategory` | `varchar(50)?` | e.g. `trip-out`, `yellowstone`, `trip-back` |
| `Tags` | `text[]` | Replaces yellowstone's per-category arrays (people, wildlife, …). GIN-indexed. |
| `Width`, `Height` | `int` | From Cloudinary |
| `UploadedBy`, `UploadedAt` | Auth0 `sub`, `timestamptz` | Audit |

The API response uses yellowstone's `photos.json` field names (`lat`, `lng`, `thumbnail`,
`medium`, `full`, and `cameraOwner`, which is now the person's display name next to `cameraOwnerId`). The size URLs are **built from the public ID on every read** instead of being
stored, so changing a size or format is a code change, not a data migration. `f_auto` lets
Cloudinary serve WebP/AVIF/JPEG per browser, which also makes iPhone HEIC uploads viewable.

### Why a GUID (v7) id

| | Auto-increment `int` | GUID v7 (chosen) |
| --- | --- | --- |
| Known before insert | No, the database assigns it | Yes. The API uses it as the Cloudinary public ID *before* saving. |
| Guessable / leaks volume | Yes (`/photos/41` means ~41 photos exist) | No |
| Index locality | Sequential | Time-ordered, so it inserts almost as well as an int (unlike random v4 GUIDs) |
| Size | 4 bytes | 16 bytes. Irrelevant at this scale. |
| Merging data from elsewhere (imports, other environments) | Collides | Doesn't |

The filename is kept as a field but not used as an identity. Two cameras can produce the same
filename, and a re-export can change it.

## Upload: `POST /api/v1/photos`

Requires the `write:photos` permission. `multipart/form-data`:

| Field | Required | |
| --- | --- | --- |
| `file` | yes | JPEG, PNG, WebP or HEIC, max **10 MB** (Cloudinary free-plan image limit) |
| `cameraOwnerId` | no | Id of an existing person. Unknown ids get 400. |
| `placeId` | no | Id of an existing place. Unknown ids get 400. |
| `dateCategory` | no | |
| `lat` + `lng` | no | Overrides EXIF; saved as `LocationSource = Manual` |
| `dateTaken` | no | ISO 8601 with offset; overrides EXIF |

The endpoint checks the file and form, then hands off to `UploadPhotoHandler`, which does the rest:

1. Validate the fields, then read EXIF (capture time and GPS) from its own in-memory copy of the upload.
2. Upload to Cloudinary as `{Cloudinary:Folder}/{id}` with `overwrite=false`.
3. Save the row. If saving fails, delete the just-uploaded image so Cloudinary has no orphans.

Responses: `201` with the photo. `400` for validation errors, or if Cloudinary rejects the file as
not an image. `502` if Cloudinary is unavailable, in which case nothing is saved.

Reading (`GET /api/v1/photos`, `GET /api/v1/photos/{id}`) requires `read:photos`. The list is
ordered by `dateTaken`, with undated photos last.

### Capture time

EXIF `DateTimeOriginal` is the camera's local time **with no time zone**. The API resolves it, in order:

1. `DateTimeOriginal` + `OffsetTimeOriginal` (EXIF 2.31; Pixel and recent iPhones write it)
2. The GPS timestamp, which is always UTC
3. `DateTimeOriginal` read as UTC, as a last resort. Send `dateTaken` to override.

It never interprets EXIF time in the **server's** time zone. np-web's
`extract-photo-metadata.mjs` does (`new Date(y, m, d, …)`), which shifts every `dateTaken` by the
difference between the camera's zone and the machine that ran the script. The sample
`PXL_20260824_031151688` (Pixel names are UTC: 03:11:51Z) is recorded as `02:11:51Z`. Keep this
in mind when importing the existing JSON.

### Cloudinary folders

`Cloudinary:Folder` is `np-api/photos` in production and `np-api/dev/photos` in Development
(`appsettings.Development.json`), so local testing never mixes with real photos. The existing
yellowstone images stay where they are (`yellowstone/<owner>/<file>`). An import would reference
those public IDs rather than re-uploading.

## Finding a location when EXIF has none

About 10% of the yellowstone photos (48 of 477) have no GPS. Common causes: the camera app's
location setting was off, the photo was taken on a device without GPS, or the file went through a
messenger or share flow that strips metadata. Upload originals where possible. Options, best first:

1. **Borrow from a companion photo (what np-web already does).** `infer-photo-locations.mjs` takes
   the location of the closest-in-time photo from a GPS-enabled camera (Nate's), within 120
   minutes. That fits a group trip well. It could move server-side later as a "suggest location"
   step that writes `LocationSource = Inferred`, with a tighter window (e.g. 30 min) for accuracy
   and interpolation between the photos before and after.
2. **Phone location history.** Google Maps Timeline is now stored on the phone. Export it
   (Settings → Location → Location services → Timeline → Export) and match photo timestamps
   against the track. This is the most accurate fallback for photos from a phone that had location
   history on but camera geotagging off.
3. **Link the photo to a Place.** Implemented: upload with `placeId` (see [places.md](places.md)). The
   photo's own point stays null, and the map falls back to the place's representative point, shown
   as approximate. yellowstone's NPS sites are good first places. The NPS API has a free key and
   returns park coordinates.
4. **Landmark recognition.** Google Cloud Vision landmark detection returns coordinates for
   well-known sights (Old Faithful, Grand Prismatic). It's paid beyond a small free tier, only
   covers famous landmarks, and needs billing enabled.
5. **Place it by hand.** A map picker in an admin UI (`PATCH` with `lat`/`lng`, saved as `Manual`)
   is the fallback that always works.

`LocationSource` exists so the map can show inferred and manual points differently (e.g. a softer
marker), and so a later, better source never gets overwritten by a worse one.

## Configuration

| Setting | Where |
| --- | --- |
| `Cloudinary:CloudName` | `appsettings.json` (`fdacst4d`; it's public) |
| `Cloudinary:Folder` | `appsettings.json` / `appsettings.Development.json` |
| `Cloudinary:ApiKey`, `Cloudinary:ApiSecret` | Secrets. Locally: AppHost parameters `cloudinary-api-key` / `cloudinary-api-secret`. Deployed: env `Cloudinary__ApiKey` / `Cloudinary__ApiSecret`. |

The API won't start if any of these is missing.
