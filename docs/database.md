# Database

The API reads one connection string: `ConnectionStrings:npdb` (env var `ConnectionStrings__npdb`).
Choosing dev vs prod is only a matter of which value that setting holds where the API runs. There
is no environment switch in code.

| Where | Database | Where the connection string comes from |
| --- | --- | --- |
| Local (default) | Postgres container started by Aspire | Generated by the AppHost |
| Local, against Neon | Neon `dev` branch | AppHost user secrets |
| CI migrations | Neon `dev` / `main` branch (direct endpoint) | GitHub Actions environment secret |
| Production | Neon `main` branch (pooled endpoint) | Hosting platform secret → env var |

## Neon setup

1. Create a Neon project. Its default branch `main` is **production**.
2. Create a branch named `dev` from `main`. Branches are copy-on-write copies of the database, so
   they're cheap. Use it for staging and for running locally against real Neon when you want to.
   You can reset it from `main` at any time.
3. Optional later: create a short-lived branch per pull request with
   `neondatabase/create-branch-action` and delete it when the PR closes.

### Connection string format

Npgsql does **not** accept the `postgresql://...` URI that Neon shows by default. In the Neon
Connect dialog choose the **.NET** format, or convert it yourself:

```
Host=ep-xxxx-pooler.us-east-2.aws.neon.tech;Database=neondb;Username=neondb_owner;Password=...;SSL Mode=Require
```

- **Pooled** (host contains `-pooler`, goes through PgBouncer): use it for the running API.
- **Direct** (no `-pooler`): use it for migrations and admin tools.

### Scale to zero

On the free plan, Neon suspends compute after a few minutes of inactivity. The first query after
that waits for the compute to wake up (typically under a second). The EF retry policy covers this.
Anything that queries the DB on a timer (for example a health probe hitting `/health`) keeps compute
awake and uses up the free compute hours. See [health-checks.md](health-checks.md).

## Running locally

**Default: container.** `dotnet run --project src/NpApi.AppHost` starts Postgres with a persistent
Docker volume and container (`ContainerLifetime.Persistent`), so data survives restarts. The
container keeps running after the AppHost stops. Remove it from Docker Desktop when you want a clean
database.

**Against the Neon `dev` branch:**

```sh
dotnet user-secrets --project src/NpApi.AppHost set Database:UseExternal true
dotnet user-secrets --project src/NpApi.AppHost set ConnectionStrings:npdb "Host=ep-...;Database=neondb;Username=...;Password=...;SSL Mode=Require"
```

Use the **direct** endpoint for the dev branch. Development applies migrations on startup, and
schema changes should not go through the pooler. To switch back:
`dotnet user-secrets --project src/NpApi.AppHost remove Database:UseExternal`.

## Migrations

EF Core migrations live in `src/NpApi.Api/Data/Migrations`. `dotnet-ef` is a local tool, so run
`dotnet tool restore` once.

```sh
# create
dotnet ef migrations add AddTags --project src/NpApi.Api --output-dir Data/Migrations

# preview the SQL
dotnet ef migrations script --idempotent --project src/NpApi.Api
```

`dotnet ef` uses `DesignTimeDbContextFactory` (it doesn't need the AppHost running). Commands that
connect to a database need `--connection "<direct connection string>"`.

**When migrations run:**

- **Development:** automatically on API startup (`ApplyMigrationsInDevelopmentAsync`).
- **Staging/production:** as a step in the deploy pipeline, **before** the new API version goes
  live. The app never migrates itself in production. If several instances all migrated on
  startup, they could race each other, and a failed migration would crash-loop the service.

Use a migration bundle, a self-contained executable that applies pending migrations:

```sh
dotnet ef migrations bundle --project src/NpApi.Api -o efbundle --self-contained -r linux-x64
./efbundle --connection "$NEON_DIRECT_CONNECTION_STRING"
```

Write migrations so they're backward compatible with the currently running version (add columns as
nullable or with defaults, then drop old columns in a later release). The old version keeps serving
traffic for a moment after the migration runs.

## Switching dev vs prod during deployment

Use **GitHub Environments** (`staging`, `production`), each with its own secrets:

| Secret | staging | production |
| --- | --- | --- |
| `NEON_DIRECT_CONNECTION_STRING` | `dev` branch, direct | `main` branch, direct |
| runtime `ConnectionStrings__npdb` | `dev` branch, pooled | `main` branch, pooled |

The same workflow job runs for both. Only the environment name changes, and that selects the secrets.
See [deployment.md](deployment.md) for the pipeline sketch.
